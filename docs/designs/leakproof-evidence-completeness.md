## Problem Statement *(unchanged)*

Indian marketplace sellers (Amazon, Flipkart) lose a material share of settlement
value inside reports nobody reads: commission overcharges, fee errors, weight
overcharges, returns that never physically return, refunds whose fees are never
reversed, unpaid orders, tax mismatches, and unexplained deductions, compounded
by claim windows that expire unfiled. Existing tools flag discrepancies; none
tell the seller what is actually collectable, through which mechanism, by which
deadline, with which evidence, and none publish measured detection accuracy.
LeakProof is a Razorpay Buildathon Track 04 (AI Finance Controller) submission
that closes that loop, judged against a rubric rewarding explainable, bounded,
human-gated agents with honest metrics.

## Demand Evidence *(unchanged, with one correction)*

Honest state: **third-party corroboration only, zero first-party evidence.**

- Headline claim: **2–5% of marketplace settlement value** (Terra Insight).
  Adjacent estimates use different bases and are cited separately, not as the
  same number: 2–3% of gross payment volume (reconciliation-industry sources),
  3–5% of GMV (Osfin, Revalsys). Citation trail kept in the repo.
- Category willingness-to-pay validated by incumbents: LogiRecon, Ecommatrics,
  TrackVid, Unicommerce, Threecolts, GoNukkad all charge money for weaker loops.
- No seller has been interviewed, named, or committed, **and none will be**:
  outreach was cut on 2026-09-04. This is now a permanent property of the
  submission rather than a gap to close, and the README says so.

## Status Quo *(unchanged)*

Manual reconciliation in Excel, 10–15 hours/week, and most sellers simply don't
do it. Alternatives: CA-led services, or dashboard-and-flag SaaS that stops at
flagging. The demo's real competitor is the boring spreadsheet.

## Target User & Narrowest Wedge

A seller operating on Amazon with roughly 100–5,000 orders/month, doing recon in
Excel or not at all. **No actual human is named, and none will be** (outreach cut).

Wedge: upload one batch (orders + Amazon settlement reports + bank statement,
plus a seller-profile config) → reconciled ledger + an exception queue where every
exception carries a computed evidence state (claim-ready, blocked with a named
blocker, not claimable with a named rule, or unexplained with a deterministic
basis) with drafted, human-gated claims for the ready ones. No integration, no
marketplace logins, no standing infrastructure.

The bank leg reconciles at **payout level** (settlement payout total ↔ bank UTR
credit) and is reported as a demonstrated reconciliation step only. It does **not**
contribute to match rate: under all-synthetic data the generator writes both sides,
so matching them evidences generator self-consistency and nothing more. Order ↔
settlement is the row-level match and the only one that feeds accuracy metrics.

## Premises *(unchanged)*

1. **P1 — Schema is public; pathology is scarce.** Amazon Settlement Flat File V2
   is column-documented by SP-API and ≥5 commercial integrators. Its shape is
   narrow (`amount-type` / `amount-description` / `amount`), not wide
   fee-per-column. Consequence: parsing, not archaeology.
2. **P2 — On Flipkart, detection ≠ claimability.** SPF eligibility gates on VMS:
   a seller without a compliant Video Management System is ineligible for SPF
   regardless of evidence quality. This premise motivated the entire evidence
   model and remains its intellectual origin, but **Flipkart is no longer built**
   (see Approaches). The premise survives in the code as a labeled hand-authored
   holdout fixture in canonical form, exercising precedence step 4 without any
   claim to Flipkart support.
3. **P3 — Encoded eligibility rules beat a third marketplace.** SAFE-T excludes
   seller-issued refunds and A-to-Z transactions, so a naive
   refund-without-reversal detector false-positives on exactly the non-claimable
   cases. Meesho and the Q&A chat are cut permanently.

## Recommended Approach — B′: Amazon-Only Evidence-Completeness Engine

Central claim, unchanged: not "we find leakage" (every incumbent's sentence) but
**"we tell you what you can actually recover, and exactly what blocks the rest."**

### Pipeline

```
ingest → parse (quarantine | UNCOVERED | CONFIG-ERROR)
  → fold into order-keyed ledger, cycle-ordered            (D20)
  → coverage-window check → OUT-OF-WINDOW                  (D20)
  → exact join: order ↔ settlement line(s)
  → payout ↔ bank UTR   [reported separately, not in match rate]
  → deduction audit against versioned, dated, cited rate card
  → deterministic exception classification (the class is assigned by
    which detector fired, never by the LLM)                (D1)
  → discrepancy-keyed dedup + overlap matrix               (D19)
  → deterministic evidence-completeness computation        (D3)
  → LLM narration + claim drafting, prose only, placeholders in
    and out                                                (D2)
  → human gate (approve | override | reject)               (D8)
  → claim pack on disk → append-only audit entry           (D8, D21)
  → reporting: 7 rupee lines + 2 match rates + metrics.json
```

### Detected error classes (6)

Numbering is preserved from the prior revision so the history stays legible.
**Classes 3 and 4 are cut**, each because it dragged an entire additional input
file into a one-week build.

| # | Class | Detector basis | Technique | Mechanism | Source files |
|---|-------|----------------|-----------|-----------|--------------|
| 1 | Commission overcharge | rate-card % vs charged | rate arithmetic | SAFE-T / support ticket | settlement + rate card |
| 2 | Fixed/closing fee error | fee-slab lookup vs charged | rate arithmetic | support ticket | settlement + rate card |
| ~~3~~ | ~~Weight/shipping overcharge~~ | **CUT** — required the catalog-dims input | | | |
| ~~4~~ | ~~Return marked returned, never received~~ | **CUT** — required the returns-report input | | | |
| 5 | Refund without fee reversal | refund event vs reversal lines | event pairing | SAFE-T / support ticket | settlement |
| 6 | Unpaid order past cycle | delivered order absent from all batches > 2 settlement cycles (~14 days) after delivery | absence | support ticket | orders + settlement |
| 7 | TCS/TDS mismatch | simplified Sec-52 TCS (1%) / 194-O TDS recompute vs reported | tax recompute | CA review (export bundle; no filing) | settlement + order values |
| 8 | Unexplained deduction | deduction with no rule basis | honest-unknown | none (investigate) | settlement |

Mechanism enum: `SAFE-T | support-ticket | CA-review | none`. GST filing is out
of scope; class 7 terminates in a CA-review export. Class 7 is deliberately
simplified, never reaches CLAIM-READY (enforced by precedence step 0b, not by
convention), and is descope rung 0.

**Inputs (4 data + 1 config):** orders CSV, Amazon Settlement Flat File V2,
generic bank CSV (date, UTR, amount, narration), seller-profile config, versioned
rate-card config. Catalog dims and the returns report are gone with detectors 3
and 4.

### Evidence-state model (all computed, none LLM-generated)

Per exception:

```
mechanism:    from the class table above
eligibility:  non-window rule checks with citations (A-to-Z exclusion,
              seller-issued-refund exclusion, ...). Window arithmetic is
              its own step, not an eligibility rule.
evidence[]:   { requirement,
                source: report-derivable | seller-suppliable | unobtainable,
                status: satisfied | missing | pending,
                source_line_ids: [..] }   # populated by the detector,
                                          # consumed by D2(b) and D8
claimed_line_id: one line, or null for absence-type findings   (D19)
blocker_kind: seller-action | timing | professional-review   (BLOCKED only)
deadline:     computed per mechanism from return-scan/refund dates against
              as_of; null only for mechanism none/CA-review. A window that
              exists but cannot be computed is NOT null — see step 3.
```

**State derivation (ordered precedence, first match wins, seven steps).**
Step 6 of the prior revision (fuzzy-match cap) is gone with fuzzy matching.

```
0.  mechanism none      → UNEXPLAINED(basis)
      basis ∈ {code-unseen, code-known-no-rule}, deterministic.
      No confidence number; the basis label is the explanation.
0b. mechanism CA-review → BLOCKED(professional-review, "CA review")
      This is what makes "class 7 never reaches CLAIM-READY" true by
      construction rather than by remembering to seed a config row.
1.  any eligibility rule fails            → NOT-CLAIMABLE(rule)
2.  filing window expired                 → NOT-CLAIMABLE(window expired)
3.  window exists, source date missing    → BLOCKED(timing,
                                              "window start date missing")
4.  any required evidence unobtainable    → NOT-CLAIMABLE(evidence unobtainable)
      Worked example (Amazon-native): seller_profile.gst_registered = false
      on a mechanism requiring a tax invoice. The invoice can never exist.
      Capability facts carry validity windows, so VMS, GST and program
      enrollment share one shape. Without the profile config this step is
      unreachable and such cases land at step 5 as
      BLOCKED(seller-action, "<item> — permanence unknown"): degraded
      honestly, never silently.
5.  any required evidence missing/pending → BLOCKED(blocker_kind, named item)
6.  otherwise                             → CLAIM-READY
```

**Queue sort:** group by state (CLAIM-READY, BLOCKED, UNEXPLAINED, NOT-CLAIMABLE),
then deadline ascending, nulls last, rupees descending. Four groups matching four
states. Expired non-claimables never sit above approvable claims.

### Rupee partition (7 lines)

The rupee line is a **pure function of (class-bucket, state)**, never a
hand-maintained parallel taxonomy:

```
class ∈ {1,2,5,6}:  CLAIM-READY   → ₹ claim-ready    ┐
                    BLOCKED       → ₹ blocked        ├─ sum = ₹ identified
                    NOT-CLAIMABLE → ₹ not-claimable  ┘
class 7:            (any state)   → ₹ tax-review
class 8:            UNEXPLAINED   → ₹ unexplained
any class, below the materiality floor → ₹ below-materiality (never queued)

₹ identified = ₹ claim-ready + ₹ blocked + ₹ not-claimable
total        = ₹ identified + ₹ tax-review + ₹ unexplained + ₹ below-materiality
```

Both identities are property tests that fail `make verify`. The prior revision's
six-line split did not close: steps 1, 2 and 4 emit NOT-CLAIMABLE for
above-materiality classes, and no line existed for it, so an expired-window
commission overcharge landed nowhere.

**₹ not-claimable, broken out by reason (rule vs window expired), is the most
persuasive number in the product.** "₹18,400 expired unfiled in the last 90 days"
is the line that makes a seller act. The prior revision discarded it.

Dispositions sitting outside every rupee line, each with its own count displayed
beside quarantine: `UNCOVERED` (category outside declared corpus coverage),
`OUT-OF-WINDOW` (delivery outside the batch's declared cycle coverage),
`CONFIG-ERROR` (category inside declared coverage but lookup failed — fails the
build), and `quarantine` (malformed rows, with reasons).

### Resolved Decisions

- **D1 Deterministic classification.** *(unchanged)* Exception class = which
  deterministic detector fired. The LLM never assigns class, mechanism,
  eligibility, or state; therefore no rupee total is LLM-influenced.
- **D2 LLM numeral ban, structural form.** The drafter prompt contains **no rupee
  amounts at all**: only `{{amt:<line_id>}}` placeholders and a deterministically
  bucketed `magnitude: minor|moderate|major` label. Any number the model emits is
  therefore invented rather than transcribed. Three checks, all run by
  `make verify` against the **committed** artifacts, with no API key and no
  network: (a) no currency-formatted token in LLM-generated fields; (a′) no bare
  numeric token equals any amount in that exception's own line set within the D3
  tolerance — vacuously true if substitution works, which makes it a tripwire on
  the substitution layer; (b) every `{{amt:...}}` resolves to a line_id inside
  that exception's own evidence set.
- **D3 Money representation.** *(unchanged)* Integer paise end-to-end. Comparison
  tolerance ±100 paise per rule (₹1). Materiality floor ₹10; below-floor
  discrepancies aggregate into ₹ below-materiality, counted and reported,
  excluded from the queue and from ₹ identified.
- **D4 Unknown `amount-description` codes.** *(unchanged)* Mapped to "unclassified
  deduction"; above floor → class-8 UNEXPLAINED; reported under ₹ unexplained,
  never silently dropped and never in ₹ identified.
- **~~D5 Fuzzy-match bounds.~~ CUT.** The matcher is an exact join on order ID.
  Rationale: on all-synthetic data the generator authors the ID messiness the
  matcher absorbs, so the fuzzy match rate measures invented noise rather than
  capability. Cutting it also removes hash-join blocking, candidate-tie
  arbitration, the candidate cap, the AMBIGUOUS disposition, precedence step 6,
  the fuzzy-basis rupee annotation, the claim-pack flag and one README limitation.
  The honesty beat it provided is covered twice over by BLOCKED(needs GST invoice)
  and the ₹ not-claimable line. Rebuilding it is the first requirement of any
  future real-data run.
- **D6 Bank leg granularity.** Payout-level only: settlement payout total ↔ bank
  UTR credit, from a generic bank CSV the generator also synthesizes. **Reported
  as a demonstrated reconciliation step, excluded from the match-rate
  denominator** — the generator writes both sides, so including it would claim
  evidential weight it does not have. Duplicate UTR credits at the same amount on
  the same day must not double-satisfy one payout. Descope rung 2.
- **D7 Quarantine denominator.** *(unchanged)* Malformed rows are quarantined with
  reasons, **remain in the match-rate denominator**, and the quarantine count is
  always displayed beside match rate.
- **D8 Approval artifact.** Approve produces a claim pack on disk: clipboard-ready
  claim text + evidence bundle (cited source rows CSV + recomputation sheet) +
  audit entry. Terminal action; the no-network-side-effects test has this
  boundary. **Approve is idempotent**: a second approve is a no-op returning the
  existing pack, with no second audit entry. **Approving a non-CLAIM-READY
  exception requires a distinct override action** that names the blocker on the
  button, marks the pack OVERRIDDEN, records `approve_override` with
  `state_before`, is counted separately, and never enters ₹ claim-ready.
  **Ordering: write the pack first, append the audit entry second**, so an orphan
  pack is detectable on chain verification rather than the log claiming an
  approval whose pack does not exist.
- **D9 Metrics batches.** Measurement batch: 500 orders, **120 seeded errors
  (20 per class × 6)**, N=5 seeds, mean ± range. Demo batch: 150 orders, ~20
  seeded errors. Framing: 120/500 is a 24% *order-share* seeding rate chosen for
  statistical power; the real-world 2–5% figure is a *value share* of settlements.
  Different bases, and the README says so in one clause.
- **D10 Measurement definitions, and the gate/publish split.** Targets, stated in
  the README next to the measured result: overall recall ≥ 0.85, per-class recall
  ≥ 0.70, precision ≥ 0.95, ₹-agreement ≥ 0.99, strict match rate ≥ 0.90.
  **No target triggers anything.** The prior revision auto-descoped on a missed
  bar; that mechanism assumed a ladder with real schedule mass, and the ladder now
  holds about four hours. Every number is published as measured, including misses.

  ```
  HARD GATES (fail `make verify`) — provably right or wrong
    CONFIG-ERROR inside declared coverage
    both ₹ additivity identities
    exactly-one-state property test
    per-order sum invariant (Σ exception ₹ ≤ order deductions)
    audit chain integrity
    D2 (a)(a′)(b) against committed artifacts
    throughput regression threshold
    D12 anti-circularity import test
  PUBLISHED, NEVER GATED — measured, not proven
    recall, per-class recall, precision, value-weighted recall,
    ₹-agreement, match rate (strict + adjusted), holdout line, baseline
  ```

  Definitions. A true positive = a flagged exception whose (order/line id, class)
  matches a manifest entry. **₹-agreement rate** = share of true positives whose
  computed amount is within ±₹1 of the manifest amount, with every disagreement
  listed individually (order, class, computed, expected, delta) rather than only
  counted. It is the only metric that tests the phrase the architecture is named
  for, and it doubles as the sharpest check on D12's two independent encodings.
  Class 8 sits inside the precision denominator. `UNCOVERED`, `OUT-OF-WINDOW` and
  `AMBIGUOUS`-style dispositions sit outside it. Generator invariant: every seeded
  error ≥ 2× the materiality floor.

  **Match rate is published two ways**, with the delta and its reconciliation:
  `match_rate_strict` = matched / all orders; `match_rate_adjusted` = matched /
  (all − class-6 flagged). The strict figure cannot improve when a detector
  over-fires, which the adjusted one can. The bank leg contributes to neither.
- **D11 Reproducibility split.** *(unchanged)* `make verify` = deterministic,
  regenerates seeded batches and reproduces every metric with zero network calls.
  `make triage` = opt-in LLM job, model + version recorded, **resumable**: per
  exception artifacts, so an API timeout mid-run does not leave a half-generated
  demo, and a partial run reports what is missing.
- **D12 Anti-circularity of ground truth.** Manifest claimability labels are
  hand-authored against cited policy text **before** the rule config is written,
  and the labels file is **frozen** (checksum recorded in `contract.py`) before any
  eligibility rule is coded. The generator's fee logic and the detector's
  rate-card config are two separate encodings of the same public sources, enforced
  by an import test asserting the generator's module graph never reaches the
  rate-card config. A 26-case hand-authored adversarial holdout (cases the
  generator never produces) guards against correlated misunderstanding; scored and
  published as its own line, never merged into headline recall/precision.

  Published beside that line: **class 5 carries 8 of the 16 frozen labels and is
  the only class touching ladder steps 1-5**, a consequence of ADR-0006. A single
  systematic error in the class-5 eligibility rules therefore moves six labels
  together. The holdout partly compensates -- H08 at step 4, H09 and H23 at step
  5, all class 1 -- but the concentration is real and is stated, not corrected.

  **Known limit, stated here and in the README:** this independence is real for
  *fee arithmetic* (two encodings of a public rate card) and weaker for
  *eligibility*, because the manifest labels and the eligibility rules are both
  read from the same login-walled policy text by the same person. The
  ₹-claim-ready-vs-manifest metric should be read with that in mind.
- **D13 Throughput.** 10,000-order batch through the deterministic path. **Measure
  it, publish the seconds, and assert in CI at roughly 3× the measured figure.**
  The prior 60s bar sat at 15–30× headroom: it catches a full cross-product but
  not the realistic 3× regression. 60s is retained as the documented outer bound.
  LLM spend only on exceptions.
- **D14 Policy-verification fallback.** *(unchanged)* SAFE-T rules encode from
  secondary sources, each carrying `verified: false` + source URL + as-of date,
  surfaced in UI and README. Unverified-but-labeled beats blocked.
- **~~D15 Donated-data handling.~~ N/A.** Outreach cut; no donated data exists.
- **D16 Demo hosting and keyless demo.** Locally-runnable. `make demo` emits a
  **self-contained `demo.html`** with the JSON inlined, openable with zero
  dependencies: a judge clones and double-clicks. `make serve` runs FastAPI for the
  live approve interaction in the video. One dashboard, two data sources; the
  approve button hides itself with no backend; a test asserts both paths render
  identically. Pre-computed triage artifacts are committed so both paths are
  keyless; `make triage` regenerates them with an API key.
- **D17 Rate-card corpus, capped and declared.** Week-1 scheduled work, capped at
  three Amazon categories, each rule dated and URL-cited. The corpus **declares**
  its coverage (category IDs + validity date ranges) rather than implying it. A
  lookup miss outside the declaration is `UNCOVERED`; a miss inside it is
  `CONFIG-ERROR` and **fails `make verify`**, naming the category, slab and
  `as_of`. Without that split a rate-card typo silently converts detectable rows
  into a documented limitation, depressing published recall for reasons that look
  exactly like the cap working as designed.
- **D18 Evaluation clock.** *(unchanged)* Every batch manifest carries an `as_of`
  date (default: the batch's max settlement date; overridable). All window
  arithmetic and the detector-6 cycle threshold evaluate against `as_of`, never
  the system clock. **Deadline arithmetic is in calendar days**, stated explicitly,
  with month-end and leap-day tests.
- **D19 One exception per discrepancy.** Dedup keys on **(order_id, class,
  claimed_line_id | null)**, not on the line. Referencing a line is free; claiming
  it is not. The prior "first detector claims the line" rule starved later
  detectors: detector 1 must reference the principal line to compute a percentage,
  which blocked detector 5 from a genuinely separate, additive finding on the same
  order. An explicit **overlap matrix** covers all 15 class pairs as
  `co-fire | mutually-exclusive | precedence(n)`; the prior revision specified
  exactly one pair. Double-counting is guarded by a per-order invariant: the sum
  of exception amounts never exceeds that order's total deductions.
- **D20 Cross-cycle composition. (new)** Settlement is a stream, not a snapshot.
  The canonical ledger is order-keyed with an append-only, cycle-ordered line list
  and a **deterministic tiebreak** for lines sharing a date. Detectors consume
  `fold(lines, as_of)`, never a raw line. The batch manifest **declares its cycle
  coverage window**; orders whose delivery falls outside it take the
  `OUT-OF-WINDOW` disposition. Detector 5 fires only when the refund is at least
  one full cycle before the batch's max settlement date, otherwise
  `BLOCKED(timing, "awaiting settlement cycle N")`. Without these, three false
  positives were live: a cycle-3 reversal invalidating a cycle-1 finding, a
  verdict that flips based on where the batch was cut, and a paid order reported
  unpaid because the seller uploaded a partial history.
- **D21 Audit log schema. (new)** Entries carry
  `{seq, prev_hash, hash, ts, as_of, actor, action, exception_id, state_before,
  state_after, amount_paise, artifact_path}`, where
  `hash = H(canonical_json(entry − hash) + prev_hash)` and `action ∈ {ingest,
  detect, classify, draft, approve, approve_override, reject, export}`.
  `make verify` **recomputes the chain** rather than comparing bytes; byte
  comparison would fail on every rerun and break D18's reproducibility guarantee.
  Recording `state_before`/`state_after` is what makes the log explain how each
  exception reached its state rather than merely receipt that something happened.
- **D22 Shared contract boundary. (new)** `contract.py` is imported by both the
  generator and the detector and holds only what both must agree on and that is
  not under test: class/mechanism/state/blocker enums, the line_id format, the
  paise type and `compare_paise`, the materiality floor, `as_of` semantics, and the
  frozen-labels checksum. Its docstring names what is deliberately absent (fee
  rates, slabs, eligibility rules, claimability labels) and why. Duplicating the
  shared vocabulary makes the manifest disagree with the detector in ways that
  look like detector bugs; sharing the excluded half kills D12.
- **D23 Detector shape. (new)** A `Detector` protocol,
  `(FoldedOrder, config, as_of) -> list[Exception]`, with detection logic staying
  fully independent per class. All detectors emit through one `make_exception()`
  that raises when `source_line_ids` is empty, when `claimed_line_id` is not among
  them, or when the mechanism disagrees with the class table. This moves a whole
  error class from render time (where it surfaces as a confusing
  placeholder-resolution failure two subsystems away) to detection time, and makes
  the class table executable rather than documentation.

**Ordering constraint that parallelism can silently violate:** S17 (the D12 labels)

### README limitations (verbatim)

- "₹ recovered" is really "₹ identified + claim-ready." Actual recovery depends on
  marketplace adjudication; filing is human-gated by design. Do not overclaim.
- Rate cards drift. Fees are versioned config, clearly dated; a production system
  would sync them continuously.
- Synthetic realism has limits. Real reports contain pathologies no generator
  anticipates. All published accuracy figures are measured against seeded
  synthetic data, and no real seller data was used at any point.
- Eligibility rules marked `verified: false` were encoded from secondary sources
  with dates; treat their outputs accordingly.
- Ground-truth independence is real for fee arithmetic and weaker for eligibility:
  the manifest labels and the eligibility rules are two readings of the same
  login-walled policy text by the same person.
- Hash-chained audit log is tamper-evident, not tamper-proof.
- Accuracy targets are stated targets, not gates. Measured results are published
  whether or not they meet them.
